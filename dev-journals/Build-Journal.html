What We Learned

A complete log of every problem we hit while converting the Telegram Content Download project into a microservice architecture — and exactly how each one was diagnosed and fixed.

0

What We Were Building

We took a Node.js monolith — a single server.js file that handled auth, Telegram reading, downloading, and Google Drive — and split it into 7 independent Docker containers that communicate over an internal network.

Before

One server.js, one modules/ folder, everything coupled together. npm run dev started the backend and Angular UI together with concurrently.

After

7 services each with their own Dockerfile, package.json, and server.js. One docker-compose.yml at root starts everything with docker compose up.

The services we created:

  • auth-service :3001 — Telegram login, OTP, 2FA, session
  • telegram-read-service :3002 — Groups, messages, photos
  • telegram-download-service :3003 — Media download
  • google-upload-service :3004 — Google Drive upload
  • google-download-service :3005 — Google Drive download
  • api-gateway :3000 — Reverse proxy, routes all traffic
  • ui-service :4200 — Angular compiled → served by nginx

Full Session Timeline

Here is every meaningful event in the order it happened — from the very first error to a successful build.

Start
Initial problem reported — npm run dev was failing with "Could not find the @angular/build:dev-server builder's node package". Root cause: the ui script in root package.json pointed to modules/user-interface but the Angular app was actually in a different location, and its node_modules were not installed.
Fix
Ran npm install inside the Angular folder to install all Angular dependencies including @angular/build.
Decision
Decided to convert to microservices — each module becomes its own Docker container. Created 7 service folders under services/, wrote all Dockerfiles, docker-compose.yml, and Makefile.
Decision
Deleted modules/ folder and root server.js — no longer needed since each service is self-contained under services/.
Error 1
npm ci requires package-lock.json — all 6 Node services failed because we created package.json files manually but never ran npm install, so no lock files existed.
Fix
Ran npm install --package-lock-only in each service folder to generate lock files without installing node_modules locally.
Error 2
ui-service lock file out of sync — the Angular project had an existing but stale package-lock.json that was missing @emnapi/core and @emnapi/runtime. npm ci refuses to run when lock file and package.json disagree.
Fix
Deleted node_modules and package-lock.json inside services/ui-service and ran a fresh npm install to regenerate a clean, in-sync lock file.
Error 3
Python / node-gyp not found in Alpine container — the telegram npm package includes bufferutil, a native C++ addon. Compiling it requires Python, make, and g++. Alpine Linux ships with none of these.
Fix
Added apk add --no-cache python3 make g++ to the builder stage of the three Dockerfiles that use the telegram package: auth-service, telegram-read-service, telegram-download-service.
Error 4
Docker Hub access denied — invalid 3-level image name — we named images as sauravmehta/content-scrapper/auth-service. Docker Hub only supports username/repository (one slash). The second slash was treated as a sub-path that doesn't exist → push denied.
Fix
Renamed images to use a dash instead of a second slash — sauravmehta/content-scrapper-auth-service. Updated both Makefile and docker-compose.yml to use the new naming.
Done
Build succeeded — all 7 images built. Ready to push with make push after docker login.

Error 1 — Could not find @angular/build

Error Could not find the '@angular/build:dev-server' builder's node package 
[1] Error: Could not find the '@angular/build:dev-server' builder's node package.
[1] npm run ui exited with code 1

Where it happened: Running npm run dev from the project root.

Root cause: The root package.json had this script:

"ui": "cd modules/user-interface && ng serve"

The Angular project existed at that path, but npm install had never been run inside it — so the node_modules folder was empty. Angular's build toolchain (@angular/build, @angular/cli) was listed in package.json but not actually installed on disk.

Fix Run npm install inside the Angular folder 
cd modules/user-interface
npm install

This installs all dependencies listed in package.json including @angular/build, @angular/cli, and TypeScript, creating the node_modules folder.

💡
Lesson: each package.json needs its own npm install In a monorepo or multi-folder project, each folder with a package.json is an independent Node project. Running npm install at the root does NOT install dependencies in sub-folders. Each sub-project needs its own install.

Error 2 — npm ci requires package-lock.json

Error npm error code EUSAGE — npm ci can only install with an existing package-lock.json 
npm error code EUSAGE
npm error
npm error The `npm ci` command can only install with an existing package-lock.json or
npm error npm-shrinkwrap.json with lockfileVersion >= 1. Run an install with npm@5 or
npm error later to generate a package-lock.json file, then try again.

Where it happened: All 6 Node service Dockerfiles during docker compose build.

Root cause: We created all the service folders and package.json files by hand. But package-lock.json — the exact dependency snapshot file — is only generated when you actually run npm install. We never did, so it didn't exist. The Dockerfiles used npm ci which is stricter than npm install and requires a lock file.

Fix Generate lock files without installing node_modules locally 
# Run this in each service folder
# --package-lock-only: generates the lock file without touching node_modules
cd services/auth-service && npm install --package-lock-only
cd services/telegram-read-service && npm install --package-lock-only
cd services/telegram-download-service && npm install --package-lock-only
cd services/google-upload-service && npm install --package-lock-only
cd services/google-download-service && npm install --package-lock-only
cd services/api-gateway && npm install --package-lock-only

The --package-lock-only flag is perfect here — it resolves all dependency versions and writes the lock file, but doesn't actually download anything into node_modules. Docker will do the real install inside the container.

💡
npm install vs npm ci — what's the difference? npm install reads package.json, resolves versions, and creates/updates the lock file. npm ci reads the lock file exactly — it won't update it or deviate from it. npm ci is faster and more reproducible — perfect for Docker and CI/CD pipelines. But it requires the lock file to already exist.

Error 3 — UI lock file out of sync

Error npm ci can only install when package.json and package-lock.json are in sync 
npm error `npm ci` can only install packages when your package.json and
package-lock.json or npm-shrinkwrap.json are in sync.
Please update your lock file with `npm install` before continuing.

Missing: @emnapi/core@1.11.3 from lock file
Missing: @emnapi/runtime@1.11.3 from lock file

Where it happened: Only in ui-service Dockerfile during docker compose build.

Root cause: The Angular project had an old package-lock.json that was generated with an older version of npm or different packages. When Angular was updated (or when packages were added), new transitive dependencies appeared — @emnapi/core and @emnapi/runtime — but the lock file was never regenerated to include them. So package.json and package-lock.json described different dependency trees.

Fix Delete stale lock file and regenerate with a fresh npm install 
cd services/ui-service

# Delete the stale lock file and node_modules
rm -rf node_modules package-lock.json

# Fresh install — regenerates a clean, in-sync lock file
npm install

After this, the new package-lock.json includes @emnapi/core and all other transitive dependencies, so npm ci inside Docker finds everything it expects.

⚠️
Why does this happen? Lock files can go stale when: (1) someone updates package.json but forgets to commit the updated lock file, (2) different npm versions generate different lock file formats, or (3) a package you depend on adds new sub-dependencies. Always commit your lock file and regenerate it when you see sync errors.

Error 4 — Python / node-gyp not found in Alpine

Error gyp ERR! find Python — You need to install the latest version of Python 
npm error code 1
npm error path /app/node_modules/bufferutil
npm error command failed
npm error command sh -c node-gyp-build
npm error gyp ERR! find Python Python is not set from command line or npm configuration
npm error gyp ERR! find Python - executable path is ""
npm error gyp ERR! find Python checking if "python3" can be used
npm error gyp ERR! find Python - "" could not be run
npm error gyp ERR! find Python **********************************************************
npm error gyp ERR! find Python You need to install the latest version of Python.
npm error gyp ERR! stack Error: Could not find any Python installation to use
npm error gyp ERR! System Linux 6.12.54-linuxkit
npm error gyp ERR! node -v v20.20.2

Where it happened: auth-service, telegram-read-service, telegram-download-service — all services that depend on the telegram npm package.

Root cause: This is a chain of dependencies:

  • Our code depends on the telegram npm package (GramJS)
  • telegram depends on ws (WebSocket library)
  • ws optionally depends on bufferutil for performance
  • bufferutil is a native C++ addon — it must be compiled from source on the target machine during npm install
  • Compiling C++ requires: Python (for node-gyp build scripts), make (build orchestrator), g++ (C++ compiler)
  • Alpine Linux has none of these by default — it's intentionally minimal
Fix Install build tools in the builder stage of affected Dockerfiles 
# Before (broken):
COPY package*.json ./
RUN npm ci --omit=dev

# After (fixed):
COPY package*.json ./
# apk = Alpine's package manager (like apt on Ubuntu, brew on Mac)
# --no-cache = don't cache the package index — keeps image smaller
# python3 = required by node-gyp
# make = build orchestrator required by node-gyp
# g++ = C++ compiler required to compile bufferutil
RUN apk add --no-cache python3 make g++ && npm ci --omit=dev

This was added to: auth-service/Dockerfile, telegram-read-service/Dockerfile, telegram-download-service/Dockerfile.

Importantly, this only runs in Stage 1 (builder). The runtime Stage 2 copies only the compiled node_modules — it never sees Python, make, or g++. The final image stays small and clean.

🔍
How to spot native addons in your dependencies Look for binding.gyp files in a package's source, or packages that list node-gyp as a dependency. Common native packages: bufferutil, utf-8-validate, bcrypt, sharp, canvas, sqlite3. Any of these inside an Alpine-based Docker image will need the build tools.

What is node-gyp?

node-gyp is Node.js's build tool for native addons. When you npm install a package with a binding.gyp file, npm automatically runs node-gyp rebuild which:

1
Calls Python to configure the build
node-gyp's configuration scripts are written in Python. This is why Python is required even though the addon is C++.
2
Runs make to compile the C++ source
The C++ source files in the package get compiled into a .node binary file specific to your OS and CPU architecture.
3
The .node file is loaded at runtime
Node.js can require() native .node files just like JavaScript modules. This gives near-native C++ performance for things like WebSocket buffer handling.

Error 5 — Docker Hub access denied (invalid image name)

Error denied: requested access to the resource is denied 
denied: requested access to the resource is denied
The push refers to repository [docker.io/sauravmehta/content-scrapper/ui-service]
tag does not exist: sauravmehta/content-scrapper/ui-service:94fc73a
make: *** [push] Error 1

Where it happened: Running make push after the build.

Two separate problems in this one error:

  • Tag does not exist — some images were never fully built (earlier build errors stopped them). You can't push an image that doesn't exist locally.
  • Access denied — Docker Hub only supports username/repository format. We were using sauravmehta/content-scrapper/ui-service which has two slashes. Docker Hub treats everything after the first slash as the repository name, so it tried to push to a repository literally named content-scrapper/ui-service — which doesn't exist and can't be created.
Fix Rename images to use dash instead of second slash 
# WRONG — Docker Hub doesn't support 3 levels
sauravmehta/content-scrapper/auth-service:latest

# CORRECT — username/repository (max 2 levels on Docker Hub)
sauravmehta/content-scrapper-auth-service:latest

Updated Makefile:

# Before
REGISTRY  ?= sauravmehta/content-scrapper

# After — split into two variables
REGISTRY  ?= sauravmehta
PREFIX    ?= content-scrapper

# Image tag becomes: $(REGISTRY)/$(PREFIX)-$$svc:latest
# Result: sauravmehta/content-scrapper-auth-service:latest

Updated docker-compose.yml:

# Before
image: ${REGISTRY:-sauravmehta/content-scrapper}/auth-service:latest

# After — hardcoded since naming is now fixed
image: sauravmehta/content-scrapper-auth-service:latest
💡
Docker Hub vs private registries — naming rules Docker Hub enforces a flat username/repository namespace. If you ever move to a private registry (AWS ECR, Google Artifact Registry, self-hosted Harbor), they support deeper paths like registry.company.com/project/team/service:tag. For Docker Hub, always use dashes to group related images.

Decision — Why services/ lives at the root

A common question: why is docker-compose.yml and services/ at the project root instead of inside each service folder?

Each service owns its Dockerfile

A Dockerfile describes how to build ONE service. It lives inside that service's folder because it only knows about that service.

docker-compose.yml is the org chart

It knows about ALL services — their ports, networks, dependencies, environment. It belongs at the project level, not inside any single service.

telegram-content-download/      ← project root
├── services/
│   ├── auth-service/
│   │   ├── Dockerfile          ← knows only about auth-service
│   │   ├── server.js
│   │   └── package.json
│   ├── telegram-read-service/
│   │   └── Dockerfile          ← knows only about telegram-read-service
│   └── ...
│
├── docker-compose.yml          ← knows about ALL 7 services
└── Makefile                    ← project-level build commands

This means from the project root you can always run:

docker compose up     # works from root — no cd needed
make build            # works from root
make push             # works from root

Lessons Learned

1. Always commit package-lock.json

The lock file pins exact dependency versions. Without it, two different machines (or a Docker build) may install different versions and behave differently. Create it with npm install and commit it alongside package.json.

2. Alpine needs build tools for native Node addons

Any npm package with C++ native code (bufferutil, bcrypt, sharp, canvas, sqlite3) requires Python + make + g++ to compile. Add apk add --no-cache python3 make g++ in the builder stage only — not the runtime stage.

3. Docker Hub only allows username/repository (two levels)

You cannot do user/group/repo on Docker Hub. Use dashes to group related images: user/project-service-name. Private registries (ECR, GCR, Harbor) support deeper paths.

4. npm ci vs npm install — use the right one

Use npm ci in Docker and CI/CD — it's faster, reproducible, and will fail loudly if lock file is out of sync (which is a feature, not a bug). Use npm install locally when you want to add or update packages.

5. docker compose build --no-cache when files change on disk

Docker caches layers aggressively. If you update a file on disk (like a lock file) but Docker has a cached layer that used the old version, it won't pick up the change. Use --no-cache to force a full rebuild when you know something changed under the hood.

6. Multi-stage builds keep the final image clean

Build tools (Python, make, g++, node-gyp) are needed to compile — not to run. By installing them only in Stage 1 (builder) and copying just the compiled output to Stage 2 (runtime), the final image has no build tools, no npm, and no unnecessary packages — smaller, faster, and more secure.
