Deep Dive

Everything we built for the Telegram Content Download project — explained from first principles so you understand not just the what, but the why.

1

Monolith vs Microservices

Before we changed anything, your project was a monolith — one single server.js file that handled authentication, reading Telegram groups, downloading media, and talking to Google Drive all at once.

⬛ Monolith (Before)

One process. One crash kills everything. You can't scale just the download feature. Every developer touches the same file. Deploy one tiny change? The whole app restarts.

✦ Microservices (After)

Each concern is its own process. Auth crashes? Downloads keep working. Need 5× more download capacity? Scale only that service. Teams own separate services independently.

When microservices make sense

SituationMonolithMicroservices
Early prototype / MVP✓ Faster✗ Overhead
Services scale differently✗ Can't isolate✓ Scale each independently
Multiple teams✗ Conflicts✓ Own your service
Different tech per feature✗ One language✓ Python, Node, Go — anything
Fault isolation needed✗ One crash, all down✓ Isolated failures
💡
The rule of thumb Start as a monolith. When you feel pain — a team stepping on each other, one feature needing 10× the resources of others, deployment risk — that's when you split. We split here because the services are genuinely independent: auth doesn't know about downloads, downloads don't know about Google.

Our Architecture

This is the full picture of how traffic flows through the system. The outside world only ever talks to the API Gateway. Every service lives on a private internal network.

Browser / Angular UI
localhost:4200
↓ HTTP requests to /api/*
API Gateway
localhost:3000
routes by path prefix
/auth/* → auth-service :3001
/groups/* → telegram-read :3002
/download/* → tg-download :3003
/google/upload → g-upload :3004
/google/download → g-download :3005
All services communicate on an isolated Docker network — unreachable from outside except through the gateway

Why an API Gateway?

In production, you don't expose 7 ports to the internet. You expose one. The gateway is the single door into your system. It can handle:

  • Routing — send each request to the right service
  • Auth middleware — check JWT tokens before any service sees the request
  • Rate limiting — throttle abusive callers in one place
  • Logging — log every request once, not in every service
  • SSL termination — handle HTTPS once at the edge
🔑
Key insight: pathRewrite When the gateway receives GET /groups/123/content it strips the prefix and forwards GET /groups/123/content to telegram-read-service. But for auth, POST /auth/sign-in becomes POST /sign-in — the /auth prefix is stripped because the auth service doesn't know it lives behind a gateway. This is what pathRewrite does in http-proxy-middleware.

Docker Fundamentals

Docker solves the "works on my machine" problem. It packages your code together with its exact runtime environment — OS libraries, Node version, config — into a portable unit.

📦 Image

A read-only snapshot. Think of it like a ZIP file of your app + everything it needs to run. Built from a Dockerfile. Stored in a registry.

🏃 Container

A running instance of an image. Like running a program from an executable. You can run 10 containers from the same image simultaneously.

📋 Dockerfile

The recipe for building an image. A series of instructions: start from this base, copy these files, run this command, expose this port.

🗄️ Registry

A server that stores images. Docker Hub is the public one. You push images to it, pull them anywhere — your laptop, a server, CI/CD.

The mental model

# An analogy:
#   Dockerfile  →  recipe (instructions)
#   Image       →  cake (built artifact)
#   Container   →  slice being eaten (running instance)
#   Registry    →  bakery shelf (storage)

# Build an image from a Dockerfile
docker build -t myapp:latest .

# Run a container from that image
docker run -p 3000:3000 myapp:latest

# Push image to Docker Hub
docker push myusername/myapp:latest

# Pull image on another machine
docker pull myusername/myapp:latest

Layers — why order matters in a Dockerfile

Every instruction in a Dockerfile creates a layer. Docker caches layers. If a layer hasn't changed, Docker reuses the cached version instead of re-running it.

⚡
Critical ordering rule Always copy package.json and run npm install BEFORE copying your source code. Your source code changes constantly. Your dependencies change rarely. This way, npm install (the slow part) is cached and only re-runs when package.json actually changes. 
# WRONG — npm install re-runs on every code change
COPY . .
RUN npm install

# CORRECT — npm install cached unless package.json changes
COPY package*.json ./
RUN npm install
COPY . .

The 7 Services

Each service is completely self-contained. It has its own package.json, server.js, Dockerfile, and .dockerignore. No service imports code from another — they only communicate over HTTP.

ServicePortResponsibilityKey Routes
auth-service 3001 Telegram login, OTP, 2FA, session management POST /send-code, POST /sign-in, POST /2fa, GET /status
telegram-read-service 3002 Read groups, messages, photos from Telegram GET /groups, GET /groups/:id/photo, GET /groups/:id/content
telegram-download-service 3003 Download media files from Telegram messages POST /download
google-upload-service 3004 Upload files to Google Drive POST /upload
google-download-service 3005 Download files from Google Drive POST /download
api-gateway 3000 Route external traffic to correct service. No business logic. All of the above, prefixed and proxied
ui-service 4200 (→80) Angular app compiled to static files, served by nginx Static HTML/JS/CSS + nginx proxy to gateway

Why does each service have a /health endpoint?

Every service exposes GET /health which returns {"status":"ok"}. This is a production standard. Load balancers, Kubernetes, and monitoring tools call this endpoint periodically to know if the service is alive. If it stops responding, traffic is redirected automatically. You can also curl it yourself to check a specific service without testing business logic.

curl http://localhost:3001/health
# → {"status":"ok","service":"auth-service"}

curl http://localhost:3002/health
# → {"status":"ok","service":"telegram-read-service"}

Dockerfile Deep Dive

Let's walk through the auth-service Dockerfile line by line. Every decision has a reason.

# ── Stage 1: Install dependencies ──────────────────────────────────────
# FROM tells Docker: start from this base image.
# node:20-alpine = Node.js 20 on Alpine Linux.
# Alpine is a minimal Linux distro (~5MB). Ubuntu is ~100MB.
# Smaller base = smaller image = faster pulls = less attack surface.
# "AS builder" names this stage so we can reference it later.
FROM node:20-alpine AS builder

# WORKDIR sets the working directory inside the container.
# All subsequent commands run from /app.
# If /app doesn't exist, Docker creates it.
WORKDIR /app

# Copy ONLY package files first — not the whole source code.
# package*.json matches both package.json and package-lock.json.
# The lock file ensures exact versions are installed, not latest.
COPY package*.json ./

# npm ci = "clean install".
# Unlike npm install, it uses package-lock.json exactly.
# --omit=dev skips devDependencies — we don't need nodemon in production.
RUN npm ci --omit=dev

# NOW copy source code. This layer only busts when code changes.
# If you only changed server.js, Docker reuses the npm ci layer above.
COPY . .

# ── Stage 2: Runtime image ──────────────────────────────────────────────
# Start fresh from the same base — no npm, no build tools, no cache.
# This is the final image that actually runs in production.
FROM node:20-alpine

WORKDIR /app

# Copy ONLY the built artifacts from Stage 1.
# --from=builder references the named stage above.
# We get node_modules and server.js. Nothing else.
COPY --from=builder /app/node_modules ./node_modules
COPY --from=builder /app/server.js ./

# EXPOSE documents which port this service uses.
# This is informational — it doesn't actually open the port.
# Port binding happens in docker-compose.yml or docker run -p.
EXPOSE 3001

# Run as the 'node' user, not root.
# Running containers as root is a security risk.
# If the container is compromised, root access = host access.
# The 'node' user is a non-privileged user built into the node image.
USER node

# CMD is the default command to run when the container starts.
# Array form (exec form) is preferred — no shell wrapping,
# so signals like SIGTERM reach the node process directly.
CMD ["node", "server.js"]

What is .dockerignore?

When you run docker build, Docker sends all files in the directory to the Docker daemon as the "build context". Without a .dockerignore, it sends node_modules too — that's hundreds of megabytes being copied on every build even though Docker re-installs them inside the container anyway.

# .dockerignore — these files are NEVER sent to Docker
node_modules        # re-installed inside the container by npm ci
npm-debug.log*      # debug artifacts
.env                # NEVER bake secrets into images
.env.*              # same for any .env variant
!.env.example       # exception: .env.example is safe to include
🚨
Never bake secrets into a Docker image If your .env file gets copied into an image and that image is pushed to a registry, anyone who pulls the image can read your API keys. Always pass secrets as environment variables at runtime — through docker-compose.yml or your cloud provider's secrets manager.

Multi-Stage Builds

Multi-stage builds let you use one Dockerfile to do heavy work (installing, compiling) in one stage and then create a clean, minimal image from only the output. The intermediate stages are thrown away.

Why this matters — image size comparison

ApproachWhat's in the imageApprox size
Single stage (naive)Node, npm, devDependencies, build cache, source maps~800MB
Multi-stage NodeNode runtime + production node_modules only~150MB
Multi-stage UI (nginx)nginx + compiled static HTML/JS/CSS only, no Node~25MB

The UI service — 3 stages

The Angular UI has the most interesting Dockerfile because it uses 3 stages and the final image doesn't even contain Node.js:

# Stage 1: Install ALL dependencies (including devDependencies)
# We need @angular/cli, typescript, etc. to compile — not at runtime.
FROM node:20-alpine AS deps
WORKDIR /app
COPY package*.json ./
RUN npm ci   # includes devDependencies this time

# Stage 2: Compile TypeScript → JavaScript bundles
# ng build reads angular.json, compiles everything, outputs to dist/
FROM node:20-alpine AS builder
WORKDIR /app
COPY --from=deps /app/node_modules ./node_modules
COPY . .
RUN npm run build   # produces: dist/ui/browser/*.js *.css index.html

# Stage 3: Serve with nginx — Node is completely gone
# nginx:alpine is ~7MB. It serves static files incredibly fast.
FROM nginx:alpine

# Copy ONLY the compiled output — HTML, CSS, JS, assets.
# Node, npm, TypeScript, Angular CLI — none of it comes along.
COPY --from=builder /app/dist/ui/browser /usr/share/nginx/html

# Custom nginx config for Angular's client-side routing
COPY nginx.conf /etc/nginx/conf.d/default.conf

EXPOSE 80
CMD ["nginx", "-g", "daemon off;"]

Why nginx for the UI?

Angular is just HTML, CSS, and JavaScript after compilation. You don't need Node.js to serve static files — that's wasteful. nginx is a battle-hardened web server purpose-built for serving static content. It handles thousands of simultaneous connections with minimal memory.

The nginx.conf — Angular routing fix

# Without this config, refreshing /groups/123 returns 404.
# Why? nginx looks for a file called "groups/123" — it doesn't exist.
# Angular routes are handled client-side, in the browser.
# So for any URL that isn't a real file, we serve index.html.
# Angular's router then reads the URL and renders the right component.

location / {
    try_files $uri $uri/ /index.html;
    # try: the exact file → the exact directory → fallback to index.html
}

# Proxy /api/* calls to the API gateway
# The Angular app calls /api/groups — nginx forwards it to the gateway.
# This means the browser never needs to know the gateway's address.
location /api/ {
    proxy_pass http://api-gateway:3000/;
}

API Gateway — Production Reverse Proxy

The gateway's job is exactly one thing: receive a request, forward it to the right service, return the response. It has zero business logic. We use http-proxy-middleware — the same library used inside Angular's dev server proxy.

const { createProxyMiddleware } = require('http-proxy-middleware');

// Service URLs come from environment variables.
// Locally: AUTH_SERVICE_URL=http://localhost:3001
// In Docker: AUTH_SERVICE_URL=http://auth-service:3001
// The code is identical — only the env var changes.
const AUTH_URL = process.env.AUTH_SERVICE_URL || 'http://localhost:3001';

// This proxy middleware intercepts every request to /auth/* and:
//   1. Strips the /auth prefix (pathRewrite)
//   2. Forwards the request to AUTH_URL
//   3. Streams the response back to the original caller
app.use('/auth', createProxyMiddleware({
  target: AUTH_URL,
  changeOrigin: true,
  // pathRewrite: remove the /auth prefix before forwarding
  // so POST /auth/sign-in becomes POST /sign-in on auth-service
  pathRewrite: { '^/auth': '' },
}));

What changeOrigin does

changeOrigin: true rewrites the Host header of the forwarded request to match the target. Without it, the downstream service receives Host: localhost:3000 (the gateway's address) instead of its own address. Some services use the Host header for CORS checks or routing, so this is important.

Environment-based service discovery

Notice the gateway doesn't hardcode http://auth-service:3001. It reads from process.env.AUTH_SERVICE_URL. This means:

  • Locally without Docker: set AUTH_SERVICE_URL=http://localhost:3001
  • In Docker Compose: set AUTH_SERVICE_URL=http://auth-service:3001 (Docker DNS resolves service names)
  • In Kubernetes: set AUTH_SERVICE_URL=http://auth-service.default.svc.cluster.local:3001

The gateway code never changes. Only config changes. This is a core principle: 12-Factor App — store config in environment variables.

Docker Compose

docker-compose.yml is an orchestration file. Instead of running 7 separate docker run commands with all their flags, you define everything once and run docker compose up.

# The version of the compose file format
version: "3.9"

# Define an internal network all services share
networks:
  app-network:
    driver: bridge   # bridge = private network on the host machine

services:
  auth-service:
    # build: tells compose to build the image from this Dockerfile
    build:
      context: ./services/auth-service   # directory with Dockerfile
      dockerfile: Dockerfile

    # image: how to tag the built image
    # ${REGISTRY:-placeholder} means: use $REGISTRY env var, fall back to "placeholder"
    image: ${REGISTRY:-placeholder}/auth-service:latest

    # env_file: load all variables from .env into this container
    env_file: .env

    # environment: override/add specific vars (takes precedence over env_file)
    environment:
      PORT: 3001

    # ports: host:container — maps container port to your laptop
    # "3001:3001" means: localhost:3001 on your machine → port 3001 in container
    ports:
      - "3001:3001"

    # networks: join the shared internal network
    networks:
      - app-network

    # restart: unless-stopped — auto-restart if the container crashes
    # (unless you deliberately stopped it with docker compose stop)
    restart: unless-stopped

  api-gateway:
    build:
      context: ./services/api-gateway
    environment:
      PORT: 3000
      # Inside Docker, services find each other by service name.
      # Docker Compose creates DNS entries for each service on the network.
      # So "auth-service" resolves to the auth-service container's IP.
      AUTH_SERVICE_URL: http://auth-service:3001
      READ_SERVICE_URL: http://telegram-read-service:3002
    ports:
      - "3000:3000"
    # depends_on: don't start gateway until these services are up
    depends_on:
      - auth-service
      - telegram-read-service
    networks:
      - app-network

depends_on — a subtle gotcha

⚠️
depends_on only waits for the container to START, not for the app inside to be READY A Node.js service might take 2–3 seconds to boot after the container starts. If the gateway starts making requests immediately, it'll get connection refused. In production, you solve this with health checks in compose (condition: service_healthy) or retry logic in the gateway. For local dev, the default behavior is usually fine.

Useful docker compose commands

# Start everything, rebuilding changed images
docker compose up --build

# Start in background (detached mode) — terminal isn't blocked
docker compose up --build -d

# Tail logs from all services
docker compose logs -f

# Tail logs from one specific service
docker compose logs -f auth-service

# See what's running
docker compose ps

# Stop all containers (keeps the images)
docker compose down

# Stop AND remove volumes (wipes any persistent data)
docker compose down -v

# Run a one-off command inside a running container
docker compose exec auth-service sh   # open a shell
docker compose exec auth-service node -e "console.log(process.env.API_ID)"

Docker Networking

This is the concept that ties everything together. Understanding Docker networking explains why services can find each other by name inside Docker, but you access them by localhost:PORT from your browser.

Two separate worlds

Your laptop has IP 127.0.0.1. Containers have their own IPs inside Docker's virtual network. Docker creates a bridge between the two — that's what port mapping (-p 3001:3001) does.

┌─────────────────────────────────────────────────────────┐
│  Your MacBook (host machine)                            │
│                                                         │
│  Browser → localhost:4200 ──────────────────────┐       │
│  curl localhost:3000 ───────────────────────┐   │       │
│                                             │   │       │
│  ┌──────────────────── Docker network ──────┼───┼────┐  │
│  │                                          │   │    │  │
│  │  api-gateway:3000 ◄────────────────────◄─┘   │    │  │
│  │       │                                       │    │  │
│  │       ├──► auth-service:3001                  │    │  │
│  │       ├──► telegram-read-service:3002          │    │  │
│  │       └──► telegram-download-service:3003      │    │  │
│  │                                                │    │  │
│  │  ui-service:80 ◄───────────────────────────◄──┘    │  │
│  └────────────────────────────────────────────────────┘  │
└─────────────────────────────────────────────────────────┘

Outside Docker: use localhost:PORT
Inside Docker: use service-name:PORT (Docker DNS resolves service names)

How Docker DNS works

When you add services to the same networks in compose, Docker automatically creates DNS entries. So inside any container on app-network:

# Inside the api-gateway container:
curl http://auth-service:3001/health       # works — Docker resolves 'auth-service'
curl http://localhost:3001/health           # fails — localhost is the gateway itself

# From your MacBook:
curl http://localhost:3001/health           # works — port mapped to host
curl http://auth-service:3001/health        # fails — 'auth-service' doesn't exist on host DNS

Makefile & Build Scripts

A Makefile gives your project a standard interface. Anyone who clones the repo can run make build, make push, make up without reading documentation. It's the convention in almost every production engineering team.

# Variables at the top — override with: make build REGISTRY=yourusername
REGISTRY  ?= placeholder           # ?= means "use this if not already set"
GIT_SHA   := $(shell git rev-parse --short HEAD)   # current commit hash

# .PHONY tells make these aren't file targets — they're commands
.PHONY: build push save load up down logs clean

build:
    @for svc in auth-service telegram-read-service ...; do \
        docker build \
            -t $(REGISTRY)/$$svc:latest \      # tag with :latest
            -t $(REGISTRY)/$$svc:$(GIT_SHA) \  # tag with git commit hash
            ./services/$$svc; \
    done

Why tag with git SHA?

The :latest tag is convenient but dangerous in production. If you deploy :latest and it breaks, how do you rollback? You don't know which version :latest was before. But if you deploy :a3f5c8b (the git commit hash), you can always redeploy the previous commit's hash. Every image is permanently traceable to an exact commit.

# Tag strategy:
your-registry/auth-service:latest     # always the most recent build
your-registry/auth-service:a3f5c8b   # permanent — exactly commit a3f5c8b
your-registry/auth-service:v1.2.0    # semantic version (optional)

docker save and docker load

Sometimes you don't have a registry — maybe you're on a secure network, or you want to send an image to a colleague. docker save exports an image as a .tar file. docker load imports it back.

# Save image to a file
docker save placeholder/auth-service:latest -o auth-service.tar

# Transfer the .tar to another machine (scp, USB, email, etc.)

# Load it back into Docker on that machine
docker load -i auth-service.tar

# Now you can run it
docker run placeholder/auth-service:latest

Registry & Image Tags

A registry is where Docker images live remotely. Docker Hub is the default public one. When you're ready to use a real registry, here's the workflow:

1
Create a Docker Hub account
Go to hub.docker.com. Your username becomes your registry prefix — e.g. sauravmehta/auth-service.
2
Login from terminal
docker login — prompts for username and password. Stores credentials locally so docker push works.
3
Build with your registry prefix
make build REGISTRY=yourusername — builds and tags all images as yourusername/service-name:latest.
4
Push all images
make push REGISTRY=yourusername — uploads all images to Docker Hub. Now anyone can pull them.
5
Pull on any machine
docker pull yourusername/auth-service:latest — works from any machine with Docker installed. No code needed.
🏭
Other registries in the wild Docker Hub is public. In companies you'll use private registries: AWS ECR (Elastic Container Registry), Google Artifact Registry, GitHub Container Registry (ghcr.io), or a self-hosted Harbor. The workflow is identical — just change the registry URL prefix.

Docker Cheat Sheet

Images

docker images                          # list all local images
docker build -t name:tag .             # build image from Dockerfile in current dir
docker rmi name:tag                    # remove an image
docker pull name:tag                   # download image from registry
docker push name:tag                   # upload image to registry

Containers

docker ps                              # list running containers
docker ps -a                           # list all containers including stopped
docker run -p 3000:3000 name:tag       # run container, map port
docker run -d name:tag                 # run in background (detached)
docker run --rm name:tag               # auto-remove container when it exits
docker stop container-id               # gracefully stop container (SIGTERM)
docker kill container-id               # force kill container (SIGKILL)
docker rm container-id                 # remove stopped container
docker logs container-id -f            # tail logs from container
docker exec -it container-id sh        # open interactive shell inside container
docker inspect container-id            # detailed JSON info about container

Docker Compose

docker compose up                      # start all services (blocking)
docker compose up -d                   # start all services (background)
docker compose up --build              # rebuild changed images before starting
docker compose down                    # stop and remove containers
docker compose ps                      # show status of all services
docker compose logs -f                 # tail logs from all services
docker compose logs -f auth-service    # tail logs from one service
docker compose exec auth-service sh    # shell into running container
docker compose build                   # build all images (don't start)
docker compose pull                    # pull all images from registry
docker compose restart auth-service    # restart one service

Cleanup

docker system prune -a                 # also remove images not used by any container
docker volume prune                    # remove unused volumes
docker network prune                   # remove unused networks
docker system df                       # show disk usage by Docker

Glossary

API Gateway

The single entry point for all client requests. Routes to the correct microservice. Handles cross-cutting concerns like auth, logging, rate limiting.

Bridge Network

Docker's default network driver for containers on the same host. Creates a virtual network where containers can talk to each other by name.

Build Context

The directory Docker sends to the daemon when building. Everything in it can be referenced in the Dockerfile via COPY. .dockerignore reduces this.

Container

A running instance of a Docker image. Isolated process with its own filesystem, network, and resource limits. Ephemeral — killed containers disappear.

Dockerfile

A text file with instructions to build a Docker image. Each instruction creates a cached layer. Order matters for cache efficiency.

Image

A read-only, layered snapshot of a filesystem. Built from a Dockerfile. Run to create containers. Stored in registries.

Layer

Each Dockerfile instruction (RUN, COPY, etc.) creates a layer. Layers are cached. Unchanged layers are reused across builds for speed.

Microservice

A small, independently deployable service that does one thing well. Communicates with other services over a network (HTTP, gRPC, etc.).

Multi-stage Build

A Dockerfile with multiple FROM statements. Each stage can copy artifacts from previous stages. Final image only contains what you explicitly copy in.

npm ci

"Clean install". Uses package-lock.json for exact versions. Faster and more reproducible than npm install. The right choice for Docker and CI/CD.

pathRewrite

In http-proxy-middleware: strip or transform the URL path before forwarding. Used so downstream services don't need to know they're behind a gateway.

Registry

A server for storing and distributing Docker images. Docker Hub is the public default. Companies use private registries (ECR, GCR, GHCR, Harbor).

Reverse Proxy

A server that forwards client requests to backend servers. The client doesn't know which server responded. nginx and the API gateway are reverse proxies.

Service (in compose)

A named container definition in docker-compose.yml. Compose manages its lifecycle, network membership, and environment.

Volume

Persistent storage that survives container restarts. Containers are ephemeral — when they stop, data is lost unless stored in a volume.
